OSPF‑alapú útvonalválasztás, cost‑hangolás és hibaelhárítás – összefoglaló dokumentáció
Ez a fejezet bemutatja, hogyan építettem fel a három routerből álló OSPF‑topológiát (SZEG_TR – DevOps – CyberSecurity), hogyan hangoltam az útvonalválasztást OSPF cost értékekkel, milyen hibákkal találkoztam, és hogyan oldottam meg őket. A cél az volt, hogy a hálózat valós vállalati működést modellezzen, és a forgalom terelése tudatos, mérnöki döntések alapján történjen.

1. A topológia felépítése és az OSPF‑tervezés
A hálózat két nagy részre oszlik:

Rózsaszín szegmens (Szeged) – több VLAN, VoIP, szerverek, kliensek, area 40

Zöld szegmens (CS Operations) – DevOps és CyberSecurity részlegek, area 50 és 60

A két oldal között három router biztosít kapcsolatot:

SZEG_TR

DevOps

CyberSecurity

A három router közötti linkek /30‑as hálózatokkal lettek összekötve, és OSPF area 0‑ba kerültek, mivel minden nem‑backbone area csak a backbone‑on keresztül kommunikálhat. Ez kulcsfontosságú volt ahhoz, hogy a két oldal LAN‑jai átjárhatók legyenek.

2. OSPF szomszédságok és alapműködés
A konfiguráció után mindhárom routeren stabil OSPF‑szomszédság jött létre:

Gigabites linkeken DR/BDR választás történt

Serial linkeken point‑to‑point kapcsolat miatt nincs DR/BDR

A show ip ospf neighbor parancs mindenhol FULL állapotot mutatott, ami azt jelenti, hogy az OSPF‑adatbázisok szinkronban vannak.

Ez fontos megállapítás volt, mert később kiderült:
ha a ping nem működik, de a neighbor FULL, akkor a hiba nem a szomszédságban, hanem az útvonalakban van.

3. A hiba: a ping nem működött a két hálózat között
A rózsaszín és zöld szegmens között a ping bizonyos hálózatokba működött, másokba nem.
A vizsgálat során kiderült:

A 192.168.38.0/24 hálózat nem jelent meg minden router OSPF‑routing táblájában.

A DevOps router nem látta ezt a hálózatot.

A SZEG_TR router rossz irányba próbálta elérni (a 36.1‑es router felé).

A probléma oka:

A CyberSecurity router nem hirdette be OSPF‑be a 192.168.38.0/24 hálózatot.
Ezért a hálózat nem jutott át a backbone‑on, és a ping elakadt.

A megoldás:

bash
router ospf 10
 network 192.168.38.0 0.0.0.255 area 60
Ezután a routing táblák helyreálltak, és a ping működött.

4. OSPF cost értékek és a forgalom terelése
A következő cél az volt, hogy:

A DevOps hálózat felé a serial link legyen a preferált útvonal.

A CyberSecurity hálózat felé viszont a gigabites link maradjon a preferált.

Ez teljesen reális vállalati igény, hiszen különböző részlegek különböző útvonalakat használhatnak optimálisan.

A cost működése
Az OSPF cost kimenő irányú metrika, vagyis:

minden router maga dönti el, melyik interfészen mennyi a cost,

a két oldal costja nem kell, hogy szimmetrikus legyen,

az OSPF a teljes útvonal összköltségét számolja.

Ezért fordult elő, hogy amikor:

Serial → cost 5

Gig0/2 → cost 100

akkor a SZEG_TR router nem a Serialt választotta, hanem a 36.1‑es router felé terelte a forgalmat, mert az összköltség ott kisebb volt.

Ez fontos tanulság:

Nem elég egy linket olcsóbbá tenni — a teljes útvonal összköltségét kell figyelembe venni.
5. A végső, működő megoldás
A SZEG_TR routeren:

✔️ A DevOps felé vezető Serial link olcsó lett:
bash
interface Serial0/2/0
 ip ospf cost 5
✔️ A 36.1 felé vezető Gig0/0 link drágább lett:
bash
interface Gig0/0
 ip ospf cost 50
Így:

DevOps felé az összköltség: 5 + X

36.1 felé az összköltség: 50 + Y

A Serial útvonal lett a legolcsóbb → a forgalom oda megy.

CyberSecurity felé viszont továbbra is a gigabites link a preferált.

Igen.
Az aszimmetrikus útvonalak teljesen normálisak:

terheléselosztás

különböző részlegek eltérő prioritása

redundancia

WAN‑optimalizáció

A módszer, amit alkalmaztunk, valós hálózati forgalom‑mérnöki technika, és tökéletesen illik egy vizsgaremekbe.

CHAP:
A CHAP lényege, hogy a jelszó soha nem megy át a hálózaton, hanem egy háromlépcsős kihívás‑válasz folyamat során MD5 hash formájában ellenőrzik. A konfiguráció Packet Tracerben egyszerű: mindkét routernek ismernie kell a másik CHAP‑felhasználónevét és jelszavát, és az interfészen engedélyezni kell a PPP‑t és a CHAP‑ot.

1) LCP (Link Control Protocol) felépül
A PPP kapcsolat első fázisa. Ha az LCP nincs „open” állapotban, CHAP nem indul el.

2) A hitelesítő router küld egy CHALLENGE üzenetet
Ez tartalmaz:

egy véletlenszerű azonosítót,

a saját nevét (hostname),

egy random értéket.

3) A másik router válaszol egy RESPONSE üzenettel
A válasz tartalmazza:

a hash értéket (MD5),

a saját nevét.

A hash így készül:

MD5(Challenge_ID + Secret + Random_Value)

4) A hitelesítő router összehasonlítja a hash-t
Ha egyezik → Success  
Ha nem → Failure és a kapcsolat bontódik.

A CHAP időnként újra megismétli a hitelesítést, így véd a replay támadások ellen.

konfig a projektben: 
SZEG_TR - 
username DevOps password Nincs1
int s0/2/0
encapsulation ppp
ppp authentication chap 
ppp chap hostname SZEG_TR
ppp chap password Nincs1 

DevOps - 
username SZEG_TR password Nincs1 
int s0/2/0
encapsulation ppp 
ppp authentication chap
ppp chap hostname DevOps
ppp chap password Nincs1

Mit jelentenek ezek?
username R2 password cisco  
Router1 azt mondja: „Ha R2 próbál hitelesíteni, a jelszava cisco.”

ppp chap hostname R1  
Ez lesz a CHAP „névmezője”, amit a másik router keres a saját username listájában.

ppp chap password cisco  
Ez a CHAP „secret”, amit a hash‑hez használ.

ppp állapotának ellenőrzése: 
 - show interfaces se0/2/0 --> itt kell keresni: Encapsulation PPP, LCP Open, Open: IPCP, CDPCP sorokat

OSPF redistribute static parancs kiadása végroutereken: 
A redistribute static parancsot elég egyetlen routeren kiadni, mégpedig azon, amelyikben a statikus útvonalak ténylegesen szerepelnek. Onnantól kezdve az OSPF‑hálózat összes többi routere automatikusan megkapja ezeket az útvonalakat OSPF external (O E2) formában.

A redistribute static parancs azt csinálja, hogy minden a routeren lévő statikus útvonalat betolja az OSPF-be, és a többi OSPF‑router felé úgy hirdeti, mintha OSPF‑en tanulta volna. Ezek az útvonalak OSPF‑ben „O E2” (external type 2) útvonalként fognak megjelenni. 

Az OSPF úgy működik, hogy bármely router, amelyik redisztribúciót végez,
LSA Type 5 üzeneteket generál a statikus útvonalakról.

Ezeket az LSA‑kat:

a teljes OSPF‑hálózat továbbterjeszti,

minden router beépíti a saját OSPF adatbázisába,

és a routing táblában O E2 (vagy ha úgy állítod: O E1) útvonalként jelennek meg.

Hogyan ellenőrzöd, hogy működik?
Ha látod az O E2 útvonalakat → működik.

ACL szűrés a távmunkás részre: 
Ez az ACL:

engedi a visszatérő TCP forgalmat (established),

engedi a két központi szerver felé menő válaszokat,

tiltja az internet felől érkező támadásokat,

engedi a router saját menedzsmentjét, ha kell.

ACL konfiguráció - 
ip access-list extended HOME_IN
 remark ---- Allow return traffic (TCP established) ----
 permit tcp any any established

 remark ---- Allow ICMP replies ----
 permit icmp any any echo-reply

 remark ---- Allow access to central servers ----
 permit ip any host 192.168.20.11
 permit ip any host 192.168.20.7

 remark ---- Block inbound traffic to the home LAN ----
 deny ip any 192.168.50.0 0.0.0.255

 remark ---- Allow everything else ----
 permit ip any any

Alkalmazás a WAN interfészre - 
interface GigabitEthernet0/1
 ip access-group HOME_IN in
